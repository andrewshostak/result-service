- [X] enforce `MAX_RETRIES` in `ResultCheckerService.handleInPlayMatch` — the config field exists but is never checked, so result check tasks reschedule indefinitely if a match stays `in_progress`
- [ ] one `check_result_task` per provider per match instead of a single task per match that fans out to all providers in `ResultCheckerService.CheckResult` — needed once a second result provider is onboarded, to properly arbitrate providers disagreeing on a match's status instead of picking the first one found. Approach: `MatchService.Create` schedules a separate task for each provider that returned the match; `CheckResult` then receives a provider-scoped task, queries only that provider's API, and updates only that provider's `provider_match` row. This avoids the `ListByMatchID` + fan-out loop in `CheckResult`, keeps each task independently retryable per provider, and makes it trivial to add/remove a provider without changing the check logic. Trade-off: task scheduling becomes more complex in `Create` (one `ScheduleResultCheck` call per provider), and `check_result_tasks` needs a `provider_id` column to carry provider context into the task handler. Until this lands, `CheckResult` resolves disagreement between providers by picking the first provider match it finds a result for; with a single provider (fotmob) this is deterministic.
